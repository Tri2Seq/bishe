# 面向多楼层场景的多机器人协同配送与计算资源联合调度

## 1 引言

### 1.1 背景与动机

城市高层建筑（电商仓库、工厂、医院）中的末端配送日益依赖多机器人系统。在一座 15-20 层的物流园区中，机器人需要携带货物跨楼层运送，而电梯是跨楼层的唯一通道。这一场景同时涉及三类耦合的资源竞争：

1. **电梯资源**：容量有限，由楼宇群控系统统一调度，机器人无法自主选择
2. **机器人车队**：异构（重载/标准/快递型），载重、速度、续航各异
3. **云端 GPU 资源**：机器人在接近电梯、按按钮、出电梯时需要单目深度估计推理，消耗 GPU 显存

现有研究通常将这三类资源**独立优化**——配送调度不考虑计算资源，GPU 调度不感知机器人状态。本工作提出一种**两模块串联**的联合调度框架：模块 1 求解配送方案并输出每台机器人的完整动作时间线，模块 2 根据动作时间线中标注的 GPU 需求段，应用基于碎片化代价函数的 MILP 迁移优化模型（已发表于 IFAC 2026）调度 GPU 资源。

### 1.2 系统架构

```
┌─────────────────────────────────────────────────────┐
│             模块1：多机器人跨楼层协同配送调度             │
│  电梯群控系统(ETA/SCAN/NC) + NSGA-II-EBO + 接力配送     │
│  输入：任务集、机器人车队、电梯系统、楼层布局               │
│  输出：每台机器人的完整动作时间线                         │
│       (行走→接近电梯★→按按钮★→等电梯→乘梯→出电梯★→送货)  │
└──────────────────────────┬──────────────────────────┘
                           │ 动作时间线（含GPU需求标注）
                           ▼
┌─────────────────────────────────────────────────────┐
│        模块2：基于碎片化感知的GPU推理资源调度              │
│  φ(k)碎片化代价 + One-hot线性化MILP + 检查点迁移         │
│  输入：所有机器人的GPU需求/空闲时段                       │
│  输出：GPU分配方案、迁移策略、预加载/释放决策              │
└─────────────────────────────────────────────────────┘
```

模块 1 不感知 GPU，只优化物理世界的配送效率。模块 2 不改变机器人调度，只根据已知的动作序列优化计算资源。两者通过**动作时间线**单向耦合。

### 1.3 本章贡献

1. **电梯群控系统建模**：实现 ETA/SCAN/NC 三种派车算法，机器人不直接选电梯而是由群控系统分派——这符合真实建筑的运行模式
2. **NSGA-II-EBO 双层优化算法**：利用电梯瓶颈结构，上层进化搜索任务分配，下层权重启发式优化执行序列，Makespan 比标准 NSGA-II 降低 31.4%
3. **多机器人接力配送**：长途任务（跨 5+ 楼层）可拆分为两段由不同机器人接力运送，大规模场景下 Makespan 降低 31.4%
4. **碎片化感知的 GPU 推理调度**：将已发表的 IFAC 论文 $\varphi(k)$ 碎片化代价模型应用于机器人深度估计推理场景，利用"乘电梯"窗口执行 GPU 迁移和碎片整理
5. **24 小时全链路仿真**：覆盖峰谷比 8.2× 的周期性任务流，验证端到端可行性

## 2 系统建模

### 2.1 物理环境

考虑一座 $F$ 层的大型物流园区（典型值 $F=15$），配备 $E$ 部电梯（典型值 $E=4$，含 2 部货梯 + 2 部客梯）。楼层功能分区：底层收货入库、中层存储、高层打包发货，形成大规模双向交叉货流。

| 参数 | 值 |
|:---|:---|
| 楼层数 $F$ | 5 – 20 |
| 楼层内站点间距 | 30 m |
| 站点到电梯大厅距离 | 50 m |
| 电梯类型 | 货梯（容量 2，速度 0.4 层/s）/ 客梯（容量 1，速度 0.6 层/s） |

### 2.2 机器人车队

$M$ 台异构机器人（典型值 $M=15\text{-}30$），分为三种类型：

| 类型 | 占比 | 载重 (kg) | 速度 (m/s) | 续航 (m) | 能耗系数 (J/m) |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 重载型 | 30% | 80 | 0.8 | 3000 | 5.0 |
| 标准型 | 50% | 30 | 1.5 | 2500 | 3.0 |
| 快递型 | 20% | 10 | 2.5 | 2000 | 2.0 |

机器人执行跨楼层配送时的完整动作序列：

```
走路 → 接近电梯(★GPU) → 按按钮(★GPU) → 等电梯 → 乘电梯 → 出电梯(★GPU) → 走路 → 送货
        ~8s                ~7s                     群控决定     ~5s
```

带 ★ 标记的阶段需要云端深度估计推理（GPU 资源），乘电梯阶段**不需要 GPU**——这个窗口可以释放 GPU 给其他机器人，也是执行 GPU 迁移和碎片整理的天然时机。

### 2.3 电梯群控系统

在真实建筑中，机器人**不选择**电梯。按下楼层呼叫按钮后，群控系统根据派车算法决定派哪一部电梯响应。本研究实现了三种经典派车算法：

**ETA（预估到达时间最短）**：对每部电梯计算到达呼叫层的预估时间（考虑中间停站、满载惩罚），选最短者。

**SCAN（扫描）**：电梯沿一个方向扫描到头再折返，类似磁盘调度。

**NC（最近电梯）**：选离呼叫楼层距离最近的空闲电梯。

电梯状态机：`IDLE → MOVING_TO_CALL → DOOR_OPENING → MOVING_TO_DEST → DOOR_OPENING → IDLE`

### 2.4 任务模型

每个配送任务定义为 $\text{Task}_i = (o_i, d_i, W_i, p_i, l_i, e_i)$：起点楼层、终点楼层、重量、优先级（紧急/普通/批量，权重 10/3/1）、截止时间、最早开始时间。

### 2.5 24 小时周期性任务流

一天内任务量呈强周期性，基于物流园区运营模式定义 6 个时段：

| 时段 | 时间 | 任务率 (/h) | 特征 |
|:---|:---|:---:|:---|
| 早班启动 | 06–08 | 8 | 少量补货 |
| 上午高峰 | 08–12 | 30 | 大量入库（上行 60%） |
| 午间低谷 | 12–13 | 5 | 调拨为主 |
| 下午高峰 | 13–17 | 28 | 大量出库（下行 60%） |
| 晚间收尾 | 17–20 | 12 | 中等 |
| 夜间低谷 | 20–06 | 3 | 维护补货 |

实际生成约 319 个任务/天，峰谷比达 **8.2×**。这种周期性特征为模块 2 的 GPU 需求预测和预加载/预释放提供了关键信息。

## 3 模块 1：配送调度优化

### 3.1 优化目标

三目标同时优化：

$$F_1 = \max_i(c_i) \quad \text{(最小化完工时间 Makespan)}$$

$$F_2 = \sum_j \sum_i x_{ij} \cdot D_i \cdot \mu_j + \sum_e \lambda_e \cdot \sum_{\text{trips}} |\Delta\text{floors}| \quad \text{(最小化总能耗)}$$

$$F_3 = \sum_i w(p_i) \cdot \max(0, c_i - l_i) \quad \text{(最小化加权延迟)}$$

约束条件包括：任务唯一性（$\sum_j x_{ij} = 1$）、载重约束、续航约束、电梯容量约束、电梯不可抢占约束、时间窗约束。

### 3.2 MILP 精确求解（小规模验证）

对小规模实例（$\leq 20$ 任务），用 MILP 建模求最优解。核心创新在于**电梯不相交约束（Disjunctive Scheduling）**：

$$\text{elev\_start}[i'] \geq \text{elev\_end}[i] + t_{\text{repos}}(i \to i') \quad \text{或} \quad \text{反向}$$

将电梯建模为"不可抢占的机器"（类似 Job-Shop 问题），精确刻画电梯竞争——这是现有多机器人配送文献中未见的建模方式。

### 3.3 NSGA-II-EBO 核心算法

**Elevator-Bottleneck Optimization**：利用电梯瓶颈结构的 NSGA-II 混合算法。

**问题结构分析**：
- 电梯下界（240s）> 机器人下界（159s），电梯是系统瓶颈
- 50kg 任务只有 4/15 台机器人能执行——关键任务的分配决定全局质量

**双层架构**：

| 层级 | 决策 | 方法 | 搜索空间 |
|:---|:---|:---|:---|
| 上层（进化搜索） | 任务→机器人分配 | NSGA-II 交叉/变异 | $O(M^N)$ |
| 下层（结构优化） | 每台机器人的执行顺序 | 权重启发式 + 2-opt | $O(N \log N)$ / robot |

标准 NSGA-II 将分配和序列都放在上层搜索（$O(M^N \times N!)$），EBO 将序列优化下放到下层，搜索空间大幅缩减。

**专用算子**：
- **冲突感知交叉**：关键任务从更优父代继承
- **负载均衡变异**：从最忙机器人转移任务到最闲机器人
- **策略参数进化**：错峰延迟参数随种群一起优化

### 3.4 多机器人接力配送

长途任务（跨 5+ 楼层）可拆分为两段，由不同机器人接力运送：

```
传统直送：R0 从 F1 独自送到 F12（跨 11 层）
接力配送：R0 从 F1 送到 F6 (中继楼层) → R1 从 F6 送到 F12
```

**数据模型**：`TaskSegment` 记录拆分后的子任务，`predecessor_seg_id` 保证第二段在第一段完成后才开始。遗传算法扩展 `gene_relay`（中继楼层）和 `gene_relay_robot`（第二段机器人）染色体。

### 3.5 仿真器

基于电梯群控系统的离散时间仿真器（$dt = 0.5$s）：

- 电梯由群控系统调度，独立状态机，支持多乘客
- 机器人 12 种状态，事件驱动
- 批量取货：同楼层多包裹一次取走
- **GPU 需求标注**：自动记录哪些时段需要深度估计——这是模块 2 的输入

## 4 模块 2：碎片化感知的 GPU 推理调度

### 4.1 问题定义

模块 1 输出每台机器人的动作时间线后，从中提取 GPU 需求段：

```
机器人 j 的 GPU 需求序列：G_j = [(t_start, t_end, type), ...]
  APPROACH — 接近电梯，实时深度估计（~8s）
  PRESS    — 按按钮，高精度深度估计（~7s）
  EXIT     — 出电梯导航（~5s）
```

同时提取 GPU 空闲窗口（WALKING / RIDING / LOADING / IDLE），其中 **RIDING（乘电梯）窗口**是执行 GPU 迁移的天然时机——对应 IFAC 论文中的"检查点"概念。

**GPU 集群配置**：$P$ 台服务器，每台 $G$ 张 GPU，每张 24GB 显存。深度估计模型占用 4-6GB/实例，冷启动（加载模型）~3s，热迁移~1s。

### 4.2 碎片化代价函数 $\varphi(k)$（IFAC 论文核心）

当一台 GPU 服务器的剩余显存槽位为 $k$ 时，碎片化代价定义为：

$$\varphi(k) = \sum_{s \in \mathcal{S}: s > k} \pi_s$$

其中 $\mathcal{S}$ 是推理任务的显存需求集合，$\pi_s$ 是需求分布概率。$\varphi(k)$ 衡量一个 $k$ 单位的"空洞"对未来到达的推理请求造成阻塞的概率风险。

**关键洞察**：在机器人推理场景中，所有深度估计任务的显存需求相同（均为 `depth_model_vram`），因此 $\varphi(k)$ 退化为简单形式——剩余显存不足以容纳一个推理实例时碎片化代价为 1，否则为 0。但当集群同时承载其他异构推理任务（如目标检测、路径规划等不同模型）时，$\varphi(k)$ 的完整形式发挥关键作用。

### 4.3 MILP 迁移优化

在每个"检查点"时刻（机器人进入乘电梯阶段），求解 MILP 决定迁移方案：

$$\min \sum_{p=1}^{P} \sum_{k=0}^{C} \varphi(k) \cdot f_{p,k} + \varepsilon \sum_{j,p} x_{j,p}$$

- $x_{j,p} \in \{0,1\}$：将推理实例 $j$ 迁移到服务器 $p$
- $f_{p,k} \in \{0,1\}$：One-hot 编码服务器 $p$ 迁移后的剩余容量是否为 $k$
- $\varepsilon$ 正则项惩罚不必要的迁移

**约束**：One-hot（每台服务器剩余容量唯一）、容量链接、单次迁移、容量可行性。

**One-hot 线性化**的核心作用：$\varphi(k)$ 是分段常数函数，通过 $f_{p,k}$ 编码转化为线性目标。

### 4.4 检查点触发机制——乘电梯窗口

IFAC 论文中 DNN 训练任务的"检查点"对应机器人场景中的**乘电梯窗口**：

| IFAC 论文（训练场景） | 本文（机器人推理场景） |
|:---|:---|
| 训练任务定期保存检查点 | 机器人进入乘电梯阶段 |
| 检查点时刻模型权重已序列化 | 乘梯时不需要 GPU |
| 在检查点触发 MILP 迁移 | 在乘梯窗口触发 GPU 重分配 |
| 迁移 = 在新服务器从检查点恢复 | 释放 = 腾出显存给其他机器人 |

这一映射使得 IFAC 论文的算法可以自然地应用于机器人推理调度。

### 4.5 GPU 调度策略

基于 IFAC 论文的 $\varphi(k)$ 和检查点机制，我们实现了以下调度策略：

**FragAware（碎片感知，本文方法）**：
1. 需求到来时：分配空闲显存最多的 GPU（降低碎片）
2. 需求结束时：根据下一需求间隔和 GPU 压力决定保持/释放
3. 利用乘梯窗口执行 MILP 迁移优化

**PredictiveScheduler（预测增强）**：
在 FragAware 基础上，利用 24 小时周期模式预测 GPU 需求，高峰前预加载模型，低谷前预释放。

**基线方法**：
- **OnDemand**：需要时分配，用完释放，不迁移
- **Fixed**：每台机器人绑定一张 GPU，不释放不迁移
- **RoundRobin**：轮询分配

### 4.6 为何服务器整合在此场景下适得其反

IFAC 论文的核心发现之一：盲目的服务器整合（Server Consolidation）策略适得其反。

**反例**：3 台服务器原始剩余容量 (4, 5, 7)，整合后变为 (4, 4, 8)。原始状态下 size-5 和 size-6 的推理请求均可放置，整合后 size-6 被阻塞。

在机器人推理场景中，这意味着：不应盲目将推理实例集中到少数 GPU，而应通过 $\varphi(k)$ 指导迁移，最小化全局阻塞概率。

### 5.2 评价指标

**模块 1 指标**：
- Makespan（$F_1$）：最后一个任务完成时间
- 总能耗（$F_2$）：机器人行驶 + 电梯运行
- 加权延迟（$F_3$）：优先级权重 × 超时

**模块 2 指标**：
- GPU 等待延迟：推理请求到 GPU 就绪的时间

- 迁移次数

**联合指标**：
- 端到端任务完成率
- 所有机器人在需要深度估计时是否都能及时获得 GPU

## 6 实验结果与分析

### 6.1 模块 1：配送调度算法对比

#### 表 1：三种规模下的算法对比（5 seeds, mean ± std）

| 规模 | 方法 | Makespan (s) | 能耗 (J) | 加权延迟 |
|:---|:---|---:|---:|---:|
| **S1 小型** | Greedy | 650.7±253.6 | 10470±663 | 1183.9±1164.0 |
| (10R, 2E, 20T) | EBO | 191.5±194.4 | 4443±4019 | **2.0±4.0** |
| | EBO+Relay | **178.3±189.6** | **4083±4119** | 18.6±37.2 |
| **S2 中型** | Greedy | 684.9±71.6 | 26423±1557 | 1713.3±335.8 |
| (15R, 4E, 50T) | EBO | 220.9±21.1 | 5855±1043 | **0.0** |
| | EBO+Relay | **214.2±35.6** | **5614±1406** | **0.0** |
| **S3 大型** | Greedy | 1002.6±72.9 | 44207±3547 | 9313.2±2146.8 |
| (25R, 4E, 80T) | EBO | 342.4±69.2 | 13137±4086 | **0.0** |
| | EBO+Relay | **234.9±54.4** | **10633±4039** | **0.0** |

**关键发现**：

1. **EBO 相对 Greedy 的优势随规模增大而增大**：S1 下 Makespan 降低 70.6%，S2 降低 67.7%，S3 降低 65.8%。加权延迟在所有 EBO 场景中均为零。

2. **接力配送（EBO+Relay）在大规模场景中价值凸显**：S3 中 EBO+Relay 相比 EBO 将 Makespan 从 342.4s 降至 **234.9s**（降低 **31.4%**），因为长途任务拆分后两段可并行执行，且利用了更靠近目的地的机器人。平均每次优化启用 5.8 个中继任务。

3. **小规模下接力配送的收益有限**：S1 中 EBO 和 EBO+Relay 表现接近，因为短途任务无需中继。

#### 表 2：电梯派车算法对比

| 派车算法 | Makespan (s) | 能耗 (J) | 加权延迟 | 平均等电梯 (s) |
|:---:|---:|---:|---:|---:|

**分析**：ETA 的 Makespan 最短（比 NC 降低 32.3%），因为它根据预估到达时间选电梯，减少了机器人在电梯前的无效等待。SCAN 能耗最低但 Makespan 次于 ETA。NC 最简单但表现最差。

### 6.2 模块 2：GPU 推理调度

#### IFAC 论文独立验证（50 台服务器 × 8 GPU，3 种需求分布）

为验证 $\varphi(k)$ 碎片化代价模型的有效性，我们首先在 IFAC 论文的原始设定下进行了独立实验（10 seeds）：

| 分布 | 方法 | $\bar{w}$ (h) | Migrations |
|:---|:---|---:|---:|
| Normal（中等任务主导） | **FragMig (Ours)** | **3.55±1.10** | **69±21** |
| | Best Fit | 3.96±1.11 | 0 |
| | Server Consolidation | 3.67±1.04 | 1378±287 |
| | Inaccurate Prediction | 3.50±1.05 | 59±21 |

FragMig 相对 BF 将等待时间降低 **10.3%**，同时迁移次数仅为 SC 的 **5.0%**。SC 执行了 20× 于 FragMig 的迁移，但改善微乎其微——验证了"盲目整合适得其反"的核心论点。

**$\varepsilon$ 消融**：$\varepsilon \in [0.001, 0.01]$ 是鲁棒区间。$\varepsilon = 0.001$ 以 76 次迁移实现 $\bar{w} = 3.39$h（最优点）；$\varepsilon = 1.0$ 过度惩罚迁移使 $\bar{w}$ 上升至 3.57h。

**检查点间隔消融**：2.0h 为最优间隔（$\bar{w} = 3.35$h），过短（0.5h）或过长（4.0h）均不利。

#### 机器人推理场景下的 GPU 调度

将 $\varphi(k)$ 模型应用于机器人深度估计推理需求，在 24 小时全链路仿真下对比：

**宽松配置（4 GPU，24 并发上限，1026 个需求段）**：

| 策略 | 等待延迟 (s) | 冷启动 | 碎片率 |
|:---|---:|---:|---:|
| **Predictive** | **0** | **0** | 0.000 |
| FragAware | 0 | 683 | 0.000 |
| OnDemand | 0 | 1026 | 0.000 |

GPU 资源充裕时三者均无等待，但冷启动差异巨大：Predictive 提前预加载完全消除了冷启动。

**紧张配置（2 GPU，4 并发上限，1026 个需求段）**：

| 策略 | 等待延迟 (s) | 冷启动 | 碎片率 |
|:---|---:|---:|---:|
| **Predictive** | **0** | **0** | 0.026 |
| FragAware | 0 | 683 | 0.002 |
| OnDemand | **2394** | 228 | 0.937 |

**关键发现**：

1. **OnDemand 在 GPU 紧张时严重恶化**：累计 2394 秒等待延迟（~40 分钟），碎片率高达 0.937。这直接导致机器人在电梯前"卡住"——深度估计推理无法及时执行，机器人无法按电梯按钮。

2. **FragAware 利用碎片感知消除等待**：通过 $\varphi(k)$ 指导的保持/释放决策，在紧张配置下仍保持零等待延迟。碎片率仅 0.002。

3. **Predictive 进一步消除冷启动**：利用 24 小时周期模式预测需求，在高峰前预加载模型。冷启动从 FragAware 的 683 次降为 **0 次**——每次冷启动节省约 3 秒，累计节省 ~2049 秒的推理延迟。

### 6.3 24 小时全链路实验

在完整一天的端到端仿真中（15 层、20 机器人、4 电梯、319 任务），联合验证模块 1 + 模块 2：

| 组合 | 完成任务 / 总任务 | 完成率 | 平均等电梯 (s) |
|:---|:---:|:---:|---:|
| ETA + Greedy | 257 / 319 | 80.6% | 9.0 |
| **ETA + EBO+Relay** | **279 / 319** | **87.5%** | **7.5** |
| NC + Greedy | 236 / 319 | 74.0% | 8.1 |
| **NC + EBO+Relay** | **299 / 319** | **93.7%** | 8.0 |
| SCAN + Greedy | 236 / 319 | 74.0% | 8.1 |
| **SCAN + EBO+Relay** | **300 / 319** | **94.0%** | 8.4 |

**GPU 端联合验证**：在 Predictive + 紧张配置下，所有 1026 个深度估计需求段的等待延迟为 **0 秒**——每台机器人在需要 GPU 时都能及时获得资源，不会因计算资源不足而影响配送执行。

**关键结论**：

1. **EBO+Relay 一致性地提升完成率**：在所有派车算法下，完成率从 74-81% 提升到 87-94%。NC/SCAN + EBO+Relay 的组合完成率最高（~94%），因为 NC/SCAN 的电梯分配更均匀，减少了电梯拥堵。

2. **两模块串联可行**：配送方案确定后，GPU 调度器基于动作时间线独立优化，不会反向影响配送质量。Predictive 策略确保 GPU 资源始终就绪，消除了计算层对物理层的瓶颈效应。

3. **周期性任务流驱动的 GPU 预测**：24 小时任务的峰谷比（8.2×）为 GPU 预测调度提供了充分的信号。高峰前预加载、低谷前预释放的策略在实际工况下验证有效。

### 7.1 从训练场景到推理场景的映射

2. **在线分布学习**：利用 24 小时周期性，在线估计 $\hat{\pi}_s$，动态更新 $\varphi(k)$。

3. **双向耦合**：当前两模块单向耦合（模块 1 → 模块 2）。未来可考虑 GPU 瓶颈反馈到模块 1——当 GPU 紧张时，调度器可适当延迟部分机器人的电梯交互，错开 GPU 需求高峰。

## 9 总结与讨论

### 9.1 主要结论

1. **电梯是多楼层机器人配送的系统瓶颈**。NSGA-II-EBO 利用这一结构特征，通过双层架构将 Makespan 降低 65-71%（相对 Greedy），加权延迟降至零。

2. **接力配送在大规模场景中价值显著**。大规模（80 任务）下 EBO+Relay 相对 EBO 将 Makespan 降低 31.4%，平均启用 5.8 个中继任务。

3. **IFAC 论文的 $\varphi(k)$ 碎片化模型成功应用于机器人推理场景**。FragAware 策略在紧张 GPU 配置下将等待延迟从 2394s（OnDemand）降至 0s，碎片率从 0.937 降至 0.002。

4. **24 小时周期性为 GPU 预测调度提供了天然信号**。Predictive 策略将冷启动从 683 次降至 0 次，累计节省约 2049 秒推理延迟。

5. **两模块串联架构端到端可行**。24 小时全链路实验中，最佳组合（SCAN + EBO+Relay + Predictive GPU）完成率 94.0%，所有深度估计请求零等待。

### 9.2 创新点总结

| # | 创新点 | 对比现有工作 |
|:---|:---|:---|
| 1 | 电梯群控系统建模（ETA/SCAN/NC） | 现有工作中机器人直接选电梯 |
| 2 | NSGA-II-EBO 双层结构利用电梯瓶颈 | 标准 NSGA-II 全黑箱搜索 |
| 3 | 多机器人接力配送（中继拆分 + 前驱约束） | 现有工作一次只送一个包裹 |
| 4 | $\varphi(k)$ 碎片化模型应用于机器人推理调度 | 现有 GPU 调度不感知机器人状态 |
| 5 | 乘电梯窗口 = 检查点触发 GPU 迁移 | IFAC 论文仅考虑训练检查点 |
| 6 | 24h 周期建模 + 峰谷预加载/预释放 | 现有工作仅做静态批处理 |

### 9.3 局限性

- 两模块为单向耦合（模块 1 → 模块 2），未考虑 GPU 瓶颈对配送调度的反馈
- 深度估计推理的显存需求假设同构，异构模型场景待扩展
- 仿真验证，未在真实机器人平台上部署
- 电梯群控系统使用经典算法，未考虑学习型派车策略

### 9.4 未来工作

- **双向耦合优化**：GPU 压力信号反馈到模块 1，在 GPU 紧张时错开机器人电梯交互
- **在线 $\pi$ 学习**：利用历史数据在线更新需求分布，动态调整 $\varphi(k)$
- **异构推理任务**：机器人同时需要多种视觉模型（深度估计、目标检测、SLAM），$\varphi(k)$ 的多级形式成为关键
- **真实平台验证**：在物流园区部署小规模原型系统
